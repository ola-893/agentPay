# ToolBuyer: buy quality information before selecting a service

ToolBuyer is a deterministic **evaluation-and-selection policy**, implemented inside a local CRE workflow. For the same task observations and configuration, its trial/selection rules produce the same result. It pays for task-specific trial answers in a benchmark credit ledger, grades them, updates uncertain quality estimates and decides whether another trial is worth its cost. It then buys the selected provider's answers on held-out tasks. It does not add a marketplace or require an LLM to make the purchasing decision.

**Billing boundary:** these purchases debit synthetic benchmark credits, expressed in six-decimal USDC-style raw units. They do not transfer USDC, fund an escrow stream, sign a wallet transaction or charge a model API. The real USDC payment lifecycle remains [the separate streaming demo](AI_AGENT_DEMO.md). ToolBuyer's live Sepolia read establishes budget eligibility; it does not reserve or spend that balance, and the contract does not enforce this selection policy.

## Run

Install the existing root and CRE dependencies, Bun and the CRE CLI, and authenticate with `cre login`. From the repository root:

```sh
npm run --silent demo:toolbuyer
npm run --silent demo:toolbuyer -- --json
```

This compiles and simulates the `toolbuyer-settings` workflow three times, once per task family. Each execution uses CRE HTTP capabilities to request real loopback provider trials, and EVM capabilities to read Circle Sepolia USDC `decimals()` and `balanceOf(payer)` at an explicit block. The host uses that same policy to verify the returned decision/trace before purchasing held-out answers. No workflow is deployed to Chainlink's network.

The default public payer is `0xe26468ae02368a75DBDBea58F367B7313942ad26`. Override it with `AGENTPAY_TOOLBUYER_PAYER`; no private key is needed or used. `SEPOLIA_RPC_URL` controls host network/block checks; CRE uses the public Sepolia RPC in `cre/project.yaml`. Both must reach the specified Sepolia block. `CRE_BIN` can specify the installed CLI. A zero balance leads to abstention, not a simulated payment. The same affordable-batch rule applies to the baselines. Each task-family/seed cohort is a separate counterfactual budget, not cumulative spending from a real wallet.

For a reproducible comparison without CRE credentials or external networks:

```sh
npm run --silent demo:toolbuyer -- --offline --seeds 17,29,43,71,97
```

`--offline` runs the same policy in Bun against real loopback HTTP providers. It reads no chain and is explicitly **not CRE simulation evidence**. It uses the configured benchmark budget in place of balance eligibility. Local listeners must be permitted. The default seed is 17; `--seeds` accepts 1–10 unique integers from 1 to 1000000 in either mode. `--json` emits one result envelope on stdout with progress on stderr. Help/config/execution exit codes remain 0/2/1. There is no `--pay` flag for this benchmark.

## Providers and tasks

| Fixture | Trial cost | Service cost per task | Behavior |
| --- | ---: | ---: | --- |
| `budget` | 30 | 80 | Cheap approximations: ignores invoice discounts, rounds USDC to cents, uses the first eligible route |
| `expert` | 90 | 300 | Costly correct implementation of these bounded tasks |
| `showcase` | 45 | 150 | Memorizes the nine published examples; returns UNKNOWN for unfamiliar inputs |

All prices are raw benchmark-credit units. Every executed trial and service answer is charged, including incorrect answers. The nine visible examples are free, as is the deterministic grading oracle. These are controlled synthetic services, not claims about actual commercial providers or model quality.

The grader can solve these bounded tasks exactly and for free. This benchmark tests the selection mechanism; it does not establish that outsourcing these particular tasks is economically necessary. Real label acquisition, verification compute and transaction gas would need their own costs before using its utility totals for a production purchasing decision.

The three task families are discounted invoice totals, six-decimal USDC amount conversion and minimum-fee route selection under a latency constraint. Trials draw fresh inputs from the same family as the intended purchase. Trial indices start at 100; evaluation indices start at 10000. Visible examples use a separate fixed seed/index range. The harness checks actual input overlap, not only task IDs. Providers receive task input, not the grading label or a visible/trial/held-out flag.

Selection completes before held-out inputs and answers are generated by the harness. The selector never receives held-out outcomes, and those outcomes do not update its beliefs or trigger reselection. Every strategy buys the exact same 20 held-out tasks per cohort. The seeds are reproducible, and the source is public; this is a selection-leakage check, not protection against a provider reading the benchmark source. Published examples do not initialize the quality prior.

## Selection and stopping rule

For each provider **within the current task family**, start with an independent Beta(1,1) prior. After `s` correct and `f` incorrect paid trials, the posterior is Beta(1+s,1+f). The report shows its mean and standard deviation; those are model-based beliefs, not a measured accuracy guarantee.

For a remaining batch of `N` tasks, choose the provider with the highest positive expected utility:

```text
U(provider) = N × (rewardPerCorrect × posteriorMean − servicePrice)
```

Abstention has utility zero. Providers whose full batch plus already-spent trial costs exceed `min(configuredBudget, observedBalance)` are infeasible. Defaults are 20 tasks, reward 1000 raw per correct answer, budget 20000 raw, at most 2000 raw spent on trials, and at most 12 trials per provider. The reward is an explicit benchmark utility assumption, not token value or a revenue prediction.

For each affordable next trial, compute the expected best batch utility after a hypothetical success and failure, weighted by the posterior predictive success probability. Subtract today's best batch utility and that trial's price. Buy the trial with the greatest positive net value; otherwise stop and buy the current best batch or abstain. The full candidate values and posterior after every observation are retained. Stopping due to a trial/budget cap is separately labeled.

This is **exact one-step expected value of sample information under the stated model**, using bounded floating-point calculations for expectations and integer prices for accounting. It is myopic: a sequence of several jointly useful trials can look unprofitable one at a time. Economic stopping can occur while uncertainty remains high. The independent, stationary Bernoulli assumption can also be wrong for heterogeneous or shifting tasks. These limits are visible in the results below; no global optimality, calibration or universal performance claim is made.

## Comparison and observed result

Baselines are declared before held-out evaluation: `cheapest` always uses budget; `fixed-showcase` always uses the provider that matches all visible examples at a lower service price than expert; `fixed-expert` always uses expert. They buy no trials. All four strategies pay their service costs, even on failures. Their separate counterfactual ledgers are not added together as one purchasing policy's costs.

The October 20, 2026 **real local CRE run**, seed 17, evaluated 60 held-out tasks:

| Strategy | Correct | Trial cost | Service cost | Total cost | Utility |
| --- | ---: | ---: | ---: | ---: | ---: |
| ToolBuyer | 44/60 | 630 | 13600 | 14230 | 29770 |
| Cheapest | 15/60 | 0 | 4800 | 4800 | 10200 |
| Fixed showcase | 0/60 | 0 | 9000 | 9000 | -9000 |
| Fixed expert | 60/60 | 0 | 18000 | 18000 | 42000 |

`utility = correct × 1000 − trialCost − serviceCost`. The showcase provider scored 9/9 on its visible examples but 0/60 on unfamiliar inputs. ToolBuyer chose expert for units and routing. For invoices, one lucky budget trial caused early stopping and only 4/20 held-out successes. **Always buying expert wins this benchmark's quality and utility comparison.** ToolBuyer spends less but does not dominate it.

The five-seed **offline** comparison (17,29,43,71,97; 300 tasks) yields ToolBuyer 228/300, cost 70715 including 2715 in trials, utility 157285. Cheapest scores 64/300, cost 24000, utility 40000. Fixed showcase scores 0/300 and costs 45000. Fixed expert scores 300/300, costs 90000 and has utility 210000. These fixed deterministic seeds are a reproducible sensitivity check, not a statistical claim about a population of providers.

Each new run writes exact configs, original CRE logs, config/log SHA-256 hashes, validated results, held-out inputs/answers, all intermediate candidate values and a reconciled credit ledger under `.local/toolbuyer/runs/<id>/`. Reply validation binds provider, task ID, quoted cost and billing mode. Provider operations are idempotent by account/provider/task ID within the process; a changed input with the same key is rejected. This demo uses local fixture HTTP GET endpoints with an internal credit ledger, not a production billing API. Failed runs retain their ledger in `failure.json`; they do not silently fall back to offline mode. Saved loopback URLs expire when that run's process closes.

Tests verify integer grading vectors, posterior calculations, exact one-step information values, budget/cap/abstention behavior, swapped replies, duplicate receipts, split separation, synthetic-provider behavior and end-to-end accounting. `docs:check` replays saved selections, grades held-out answers again, reconciles costs, and checks original CRE log/config hashes. It does not establish a new chain read, DON identity or independent service-quality attestation. All services and the grader run under the same operator in this demonstration.

[Chainlink's CRE overview](https://docs.chain.link/cre/overview) explains that local simulation compiles to WASM and makes real API and EVM calls; it does not turn this benchmark ledger into onchain payment enforcement.
